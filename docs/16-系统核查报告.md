### 🔴 H1. Hermes 长期记忆存有「过期且危险」的制卡对策

**现象**：`/home/hermes/.hermes/memories/MEMORY.md` 里记着「anki_add.py 日期硬编码为空 → 对策：按 dry-run 输出手写 JSON、走 anki_cli.py add」。而现行 anki_add.py v5.5 已支持 `--date` 自动回填，SKILL.md 明令「必须用脚本，不许手写 JSON」。

**① 根因**：设计问题——自我复盘记忆没有过期/冲突检测机制；一条针对旧版本的 workaround 被永久保留，且其指引（绕过脚本）与现行教材直接冲突。模型读记忆时无法判断哪条更新。
**② 方案**：
- A：清理这条记忆（改写为「日期已由脚本兜底，一律走 anki_add.py」）
- B：记忆规范加「记教训必须注明失效条件」
- C：在 anki_cli.py `add` 入口加日期兜底（与 anki_add.py 同款），即使模型绕过脚本也有底线
**③ 推荐**：A + C 组合。理由：A 消除误导源（记忆是模型每回合都读的，权重高于一次性的 SKILL）；C 提供第二道底线（防御深度）。B 是长期规范改进，随后补。
**④ 把握**：记忆内容与现状矛盾、墨苍离 21 张模型卡日期为空、混入「目录」垃圾卡——均为实测事实，判断把握**高**。是否需要 C（改 anki_cli.py）是权衡，需你点头。
**⑤ 下一步**：改 MEMORY.md → `systemctl restart hermes-gateway` → 你飞书发一条实测。

### 🟠 M4. 飞书 WebSocket 周期性掉线重连

**现象**：gateway 日志 9-26 全天 6+ 次 `ping timeout / no close frame`，约 30–60 分钟一次，当前自愈但掉线窗口内消息可能延迟或丢失。

**① 根因**：待定——最大嫌疑是 1G 内存压力（free 长期 64–193MB）导致 heartbeat 线程饿死；Lark SDK 心跳参数为次要嫌疑。
**② 方案**：
- A：加监控（gateway 状态页/日志里加掉线计数，掉线>阈值告警）
- B：内存治理（清理 /tmp、停掉非必要进程、必要时升配置）
- C：查 Lark SDK 心跳/重连参数能否放宽
**③ 推荐**：A + B。理由：先量化再优化；内存是这台机器所有问题的公共根因。
**④ 把握**：掉线事实（高）；根因判断（中）——需 A 的数据佐证。
**⑤ 下一步**：我加一个只读掉线统计脚本 + 清理建议清单。

**② 方案**：

**③ 推荐**：A + C（收窄 hermes 的 sudoers 到白名单命令）。理由：最小权限是最可靠护栏，且不影响制卡流程。
**④ 把握**：off 的事实（高）；sudoers 收窄的安全收益（高）；具体白名单需你决策。
**⑤ 下一步**：我列 hermes 实际用到的 sudo 命令清单 → 你确认白名单 → 改 sudoers。
