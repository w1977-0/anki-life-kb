## 二、核查方法（标准如何落地，以及我自己的三次口径纠错）

沿用上一轮的四条数据基线（改法见下），新增主机层六维，每项都用实测数字而不是「看起来正常」：

4. **服务层**：`systemctl`（含 NRestarts/MemoryCurrent）、`list-timers -p LastResult`、备份服务 journal 全文、`docker inspect`（RestartCount/OOMKilled/Memory）。
5. **安全层**：`sshd -T` 生效值、sudoers 逐文件、`sudo -l -U hermes`、auth.log 全量 zgrep 归属、元数据服务器查 OS Login/IAP、`iptables -S` 全链、SUID/world-writable 扫描。

**我自己的三次口径错误（必须记录，否则会传染给下一任）**：

### 🟠 M1　logrotate 红灯常驻（唯一 failed 单元），已连续 ≥3 天失败

**① 现象**：`systemctl --failed` = `logrotate.service`。journal 每天 00:19 UTC 报：
`error: rsyslog.bak-20260916:1 duplicate log entry for /var/log/syslog`(及 mail/kern/auth/user/cron 六条) → `found error in file rsyslog.bak-20260916, skipping` → `Main process exited, code=exited, status=1/FAILURE`。09-24 / 09-25 / 09-26 连续三次同样失败（`LastTriggerUSec` 显示 timer 正常触发）。

**② 根因**：实现问题——某任 agent 于 09-16 备份 rsyslog 配置时**把 `.bak` 留在了 `/etc/logrotate.d/` 里**，logrotate include 整个目录 → 同一批日志文件被声明两次 → 报错退出。
**关键澄清**：轮转本身**仍在生效**（logrotate 跳过出错文件后继续处理其余配置）——`auth.log.1/.2.gz…/.7.gz` 覆盖到 09-21、`access.log.1/2.gz` 存在，journald 有独立上限 `SystemMaxUse=200M`（实测 161M）。所以这是 **M（不紧急但必须修）**，不是数据风险。真正的伤害是：① 红灯天天在，将来真出配置错误会被当成同一堆噪音忽略；② 该 `.bak` 的声明是 `rotate 7 / daily / maxsize 50M`，与正式的 `rotate 4 / weekly` 不一致，若哪天顺序变了，保留策略会静默漂移。

**③ 方案**：**A**：`sudo mv /etc/logrotate.d/rsyslog.bak-20260916 /root/skill-backups/`（或 `/root/logrotate-backups/`）→ `sudo systemctl start logrotate` 验证 exit 0 → `systemctl --failed` 归零。
**B**：改 `.bak` 后缀让 logrotate 忽略（`.bak` 不被忽略，logrotate 只忽略 `*~`、`*.rpmsave` 等）——不如 A 干净。
**C**：放着不管，红灯常驻。

**④ 推荐**：**A**。理由：一条 mv + 一次验证，风险为零，且把「failed 单元数」重新变成可信信号。**注意**：这与上一轮待办的 L3/L4 是同一类问题（备份文件放错目录），可一并处理。
**⑤ 把握**：**高**（错误信息与文件 mtime `Sep 24 04:31` 目录列表均实测）。
**⑥ 下一步**：等你点头执行；验收 = `systemctl --failed` 空 + `journalctl -u logrotate` 最近一次为 exit 0。

### 🟠 M2　「网关天天崩」是假象，真问题是**重启后最长 6 分钟收不到消息**

**① 现象（近 14 天实测）**
- systemd 记录：`Stopping hermes-gateway` **34 次**，`Failed with result` **35 次**，退出码分布 `status=1/FAILURE` ×33、`killed 9/KILL` ×1、`75/TEMPFAIL` ×1。**34 : 35 ≈ 1:1** → 每次「失败」都紧跟一条人为 `systemctl restart`（Hermes 优雅退出返回 1，systemd 就记一次 failure）。单元配了 `StartLimitIntervalSec=0` + `Restart=always`，所以每次都自动拉起。
- 真正的自发异常：`09-24 20:23:45` 一次 SIGKILL（停止超时后 systemd 强杀）。39 条 Traceback **全部**落在 `lark_oapi/ws/client.py:_receive_message_loop`（就是 WS 掉线本身，没有别的异常类型）。`SAFETY_ABORT / SafetyError / FULL_UPLOAD / FULL_SYNC` = **0 次**，制卡链路没被这些炸过。
- **冷启动窗口（这才是损失）**：`hermes update` 后未重启的陈旧告警每次启动都出现；启动时 `Failed to load plugin 'feishu-platform': load timed out after 10s` → `No adapter available for feishu` → `Gateway started with no connected platforms` → `feishu connect timed out after 30s` → 退避 60s → 120s。实测两次：09-24 20:45 重启 → 20:48:45 连上（**3.5 分钟**）；09-25 13:53:38 重启 → 13:59:36 连上（**6 分钟**）。
- 稳态（不重启时）的掉线自愈很快：`no close frame` → SDK `trying to reconnect for the 1st time` → 实测恢复耗时 3s / 6s / 9s / 13s / 26s / 33s。

**② 根因**：实现+配置——e2-micro 冷启动本身慢（内存峰值 407–540MB、伴随 swap，见 M4），而 Hermes 的插件加载超时是 10s、连接超时 30s，**超时阈值比机器冷启动时间还紧**；`exit 1` 的退出语义又把每次人为重启变成一条 failure 日志，污染故障信号。

**③ 方案**
- **A0**（新增，来自收尾核验）：`hermes gateway status` 打印 **`⚠ Installed gateway service definition is outdated — Run: sudo hermes gateway restart --system`** —— 现在装的 unit 文件比 Hermes 自带模板旧（主 unit mtime 停在 09-24 16:44），这也解释了每次启动都出现的「update 后未重启、模块新旧混用（mixed sys.modules）」告警。一次受控刷新（在维护窗口内做）可能顺带改掉 `exit 1` 的退出语义与超时默认值。**先只读 diff**：`hermes gateway status` 输出与 `/etc/systemd/system/hermes-gateway.service` 对比，确认差异再执行。
- **A**：运维纪律——「能不 restart 就不 restart」（SKILL.md 类改动才必须重启；MEMORY.md/配置多数可热加载），且必须重启时**在飞书里预告 6 分钟静默窗口**，重启后主动 `journalctl` 确认出现 `connected to wss://msg-frontier`，而不是只看 `active`。
- **B**：给单元加 `Type=exec` + 合理的 `TimeoutStartSec`，并把 feishu 插件加载超时（Hermes 侧）放宽到 30–60s；或加一个 `ExecStartPost` 健康探测脚本（轮询 `gateway_state.json` 的 `platforms.feishu.state == connected`，60s 内不 connected 就报警）。
- **C**：不改退出语义（治标难度量高），只在监控里把「紧跟 Stopping 的 Failed」判为重启而非故障。

**④ 推荐**：**A + B（只取 ExecStartPost 健康探测那半）**。理由：A 零成本、立刻减少 6 分钟窗口的发生次数；B 的后半段（探测 connected）把「服务 active 但平台没连上」这个静默失效变成显式失败——这正是本轮最容易吃掉用户消息的形态。改单元文件属配置变更，需你点头。
**⑤ 把握**：**高**（时间戳逐条实测）。放宽 Hermes 插件超时的具体参数在哪里配（是 config 还是常量）我还没定位，属**未验证项**。
**⑥ 下一步**：A 写进 SKILL.md/交接单的操作节；B 的探测脚本我可以先写成只读校验（不碰单元）给你看效果。

- **绕过点**：`docker:x:1001:<SSH用户>,hermes,workbuddy-ai-agent`。**hermes 仍在 docker 组** → 一条 `docker run -v /:/host` 即回到 root，收窄 sudoers 的收益被这条抹平。<SSH用户> 还在 `lxd` 组（同类风险）。
- **sudoers.d 残留**：`90-codex-temporary`（09-05，`<SSH用户> ALL=(ALL:ALL) NOPASSWD: ALL`）——名字写着 temporary，与 google_sudoers 重复授予同一能力；`%google-sudoers NOPASSWD:ALL` 的组成员是 `<SSH用户>,workbuddy-ai-agent`。OS Login 侧**目前不构成入口**（元数据 `enable-oslogin` 未设置=404、`google-oslogin-cache` inactive、`trustedusercakeys none`、passwd 里 0 个 google 用户），但一旦项目级打开 OS Login，这条 grant 立刻变成「IAM 持有者免密 root」。
- **副本权限纵深不齐**（⚠ 本条结论已由第二轮体检 docs/18 §7-🟢5 实测修正）：`sync/anki` 目录 0755 + `collection.anki2` 0644，而工作库是 0600。我原先据此写「任何本地账号都能读全库」，**这是错的**——上层 `/var/lib/anki-autocards` 与 `sync` 都是 750 hermes，路径遍历先被挡住；第二轮用 `sudo -u www-data` / `sudo -u nobody` 实测均 `Permission denied`。所以**不构成暴露**，只是纵深不一致（若有人把上层改成 755，0644 立刻变成全机可读）。
- **凭据落日志**：komari agent 的 token 出现在 ① 进程命令行（`ps` 全局可见）② nginx access.log 的 URL query 里（`access.log.1` 实测 **585 条** `token=`）。日志 `-rw-r----- www-data:adm`，而 <SSH用户> 在 adm 组。另：nginx komari 站**没有任何应用层鉴权/限速**（proxy_pass 直通，含 websocket upgrade），3 天内 60 次扫描器命中 `/.env`、`/wp-admin`、`/.git` 等路径。
- **好消息**：`sshd` = 10.0p1-7+deb13u4，`permitrootlogin no` / `passwordauthentication no` / pubkey only / `MaxAuthTries 6`；近 14 天认证失败 **0** 次；iptables 末尾对 80/443 有 **DROP** 兜底，除 22 外无公网入口；所有内部服务绑 127.0.0.1；docker 端口映射全部 `127.0.0.1:` 前缀；无空密码账号；无异常 SUID；`/etc` 无 world-writable。

**② 根因**：多任 agent 各自加授权（codex 临时、hermes-agent、workbuddy-ai-agent、google 默认），**无人做过减法**；最小权限只做在了 sudoers 这一层，没做在组这一层。

**③ 方案**
- **A（收 docker 组）**：把 hermes 移出 docker 组——制卡链路不需要它（Wallos/Komari 走 MCP 与 HTTP，实测 hermes 的 MCP 工具只连本地端口）。同时评估把 <SSH用户> 移出 `lxd`。
- **B（清授权残留）**：删 `/etc/sudoers.d/90-codex-temporary`（若 <SSH用户> 已在 google-sudoers 得到同等能力，删了不改变权限；否则改为把 <SSH用户> 加进 sudo 组的常规写法）。
- **C（副本权限）**：`chmod 750 /var/lib/anki-autocards/sync/anki && chmod 640 sync/anki/collection.anki2 media.db`（属主已是 hermes:hermes，syncserver 以 hermes 运行 → 不影响服务；需实测一次手机同步确认）。
- **D（token 不落日志）**：nginx 给 `/api/clients/v2/rpc` 单独 `access_log off;`，或改 komari 用 header 传 token（后者是 komari 侧行为，未必可改）。

**④ 推荐**：**C + B 先做**（低风险、纯收口），**A 次之**（需先确认没有 hermes→docker 的隐藏依赖），D 视你对 komari 日志的在意程度。
**⑤ 把握**：A 的风险点把握**中**（移组后若某个 agent 功能依赖 docker 会当场失效——需要一次带回归的验证）；B/D 把握**高**；C 经第二轮实测确认**不构成暴露**，降级为纵深加固（见 docs/18 🟢-5），不必急。
**⑥ 下一步**：我列出「移出 docker 组」的影响面清单（谁在用 docker：4 个容器由 dockerd 托管，不需要 hermes 权限）→ 你确认 → 逐条执行 + 回归（飞书发一条制卡、手机同步一次、komari 面板打开一次）。

### 🟠 M4　上轮 M4（飞书 WS 掉线）结项：内存假说**部分成立**，但不是主因

**量化结果（替代上轮「6+ 次/天」的估计）**
- 近 7 天日志行计数：`ping timeout` **12**、`no close frame` **44**、`reconnect` **32**、`WebSocket` **32**。每次掉线在日志里成对打印（`[Lark]` 前缀 + 裸 logger 各一条）→ **真实掉线次数 ≈ 22–30 次/7 天 ≈ 3–4 次/天**。按天（含重启噪声）：09-20 46 / 21 8 / 22 40 / 23 10 / **24 113** / 25 27 / 26 71。掉线在 24 小时内均匀分布（0–23 时都有，峰值 02/06/16 时各 10 行）。
- 每次稳态掉线的**自愈耗时 3–33 秒**（实测 6 个样本），Lark SDK 自己重连，不需要人工。
- **消息丢失窗口主要在重启后**（见 M2：3.5–6 分钟），不是稳态掉线。

**内存关系（上轮假说的定量检验）**
- 支持的一面：Hermes 自己反复打 `kanban dispatch: system memory pressure is elevated; limiting to at most 1 new work`；gateway cgroup `MemoryPeak 407.1M / swap peak 334.7M`（另几次 life 为 540.2M/377.8M、477.1M/375.6M、420M/379M）；整机 `PSI memory some avg60=3.03 full avg60=2.88`；可用内存长期 213–259MB / 964MB；swap 已用 863–971MB。
- 反对/未证的一面：**近 14 天 OOM kill = 0 次**（内核日志计数为 0，systemd-oomd inactive）；掉线时刻与内存峰值的**逐点相关性我没取到**——Komari 面板在线（`127.0.0.1:25774` HTTP 200、agent 已跑 2 天 20 小时）但历史指标存在容器可写层里，我这条路没读到（`docker/volumes` 下只有 docker 自己的 db）。
- **结论**：「内存紧张是这台机器所有问题的公共根因」这句上轮判断，方向对、但**不足以解释 WS 掉线**（无 OOM、自愈只需秒级）。真正的可执行杠杆是 M2（重启成本）和 L1（/tmp 白占 280MB 内存）。

**方案**：① 先做 L1（免费回收最多 280MB）与 M5（磁盘/备份治理），再看掉线频率是否下降；② 若要定量验证内存↔掉线，就用 Komari 面板导出 7 天内存曲线 + 我的 `journalctl` 掉线时间戳做对齐（需要面板登录，属**未验证项**）；③ 上轮建议的「掉线计数告警」——**建议改为「feishu 未 connected 告警」**（M2 的 ExecStartPost 探测），因为掉线本身自愈太快、告警意义有限，而 connected 失败是真丢消息。

## 六、给下一任的可复用要点（本轮踩到的）

1. **裸 sqlite3 读 Anki 库必须先注册 `unicase` collation**，否则 `integrity_check`、`decks`、`tags` 全报假失败。
2. **读库一律三文件快照 + 落 `/var/tmp`（磁盘）**，别落 `/tmp`——那是 tmpfs，等于再吃掉一份内存；ro 直开真库不仅被锁（`anki-syncserver` 独占），还会在备份目录留 wal/shm 边车。
3. **口径要写清楚**：`usn=-1` 才是脏（`usn>0` 正常）；`queue=-1` 是隐藏、`-50` 才是挂起；`systemd` 的 `Failed with result 'exit-code'` 紧跟 `Stopping` 就是人为重启。这三条都差点让我报错。
4. **别在 24h 窗口上看平均值下结论**（我据此误判了「2 分钟同步环」）；按小时/按天拆开才看得见是不是突发。
5. **测量本身就是负载**：`du -x /`、`find`、`docker stats` 会让磁盘忙碌冲到 95%、wa 冲到 76%。要判 IO 健康必须空载复测。
6. 权限判定不能用 `sudo test -r`（root 什么都读得到）；`grep -c google` 漏 `Google` 是大小写坑。
