**🟡-1　重启 hermes-gateway 后最长 6 分钟收不到飞书消息**
- 发现了什么：14 天里 `Stopping hermes-gateway` 34 次、`Failed with result` 35 次（几乎 1:1，说明绝大多数「失败」是人为 restart 时 Hermes 以 exit 1 退出被 systemd 记成 failure）。冷启动现场日志：`Failed to load plugin 'feishu-platform': load timed out after 10s` → `No adapter available for feishu` → `feishu connect timed out after 30s` → 退避 60s → 120s。实测两次端到端恢复：09-24 20:45 restart → 20:48:45 连上（3.5 分钟）；09-25 13:53:38 → 13:59:36 连上（**6 分钟**）。服务 `active` 但平台没连上，这段时间发来的消息进不来。
- 可能的原因：e2-micro 冷启动本身就慢（内存峰值 407–540MB 且伴随 swap 换入），而插件加载超时是 10s、连接超时 30s，**阈值比机器实际启动时间还紧**；`Restart=always` + `StartLimitIntervalSec=0` 让服务永远拉起，掩盖了「起来了但没连上」。另外 `updates.pre_update_backup=false`、每次启动都打 `Installed gateway service definition is outdated`，说明 update→restart→unit 刷新这条链没有收尾。
- 建议怎么处理：① 操作纪律：非必要不 restart（改 SKILL/MEMORY 才必须），重启前在飞书里预告静默窗口，重启后确认 `journalctl` 出现 `connected to wss://msg-frontier` 而不是只看 `is-active`；② 用一次受控维护刷新 unit（`hermes gateway restart --system` 之前先只读 diff 出改了哪些行）；③ 可选：`ExecStartPost` 加一个轮询 `gateway_state.json.feishu.state==connected` 的 60s 健康探测，把「静默失联」变成显式失败。**需要授权，且第 ② 项会重启服务。**

**🟡-2　logrotate 每天报失败（连续 7/7 天），把「真故障」变成噪音**
- 发现了什么：`systemctl --failed` 里唯一的失败单元就是它；近 7 天 `Failed to start` 计数 7。错误固定：`error: rsyslog.bak-20260916:1 duplicate log entry for /var/log/{syslog,mail,kern,auth,user,cron}.log` → `found error in file rsyslog.bak-20260916, skipping` → exit 1。同时实测轮转**其实还在生效**（`syslog.1`+6 个 `.gz`、`auth.log.1`+6 个 `.gz`、日期连续）。
- 可能的原因：09-16 某次改 rsyslog 配置时把 `.bak` 直接留在了 `/etc/logrotate.d/`，logrotate include 整个目录 → 同一批文件被声明两次；且 `.bak` 那份写的是 `rotate 7/daily/maxsize 50M`，与正式的 `rotate 4/weekly` 不一致。
- 建议怎么处理：把 `/etc/logrotate.d/rsyslog.bak-20260916` 移到该目录外（例如 `/root/logrotate-backups/`），手动 `systemctl start logrotate` 验一次 exit 0，验收标准 = `systemctl --failed` 归零且第二天 00:19 UTC 不再失败。**需要授权（一次 mv + 一次 start）。**

**🟡-3　凭据明文写进日志/命令行（范围限于本机）**
- 发现了什么：① journald 明文记录飞书 WS 建立 URL 里的 `access_key=` 与 `ticket=`（每次连接一条）；② komari agent 的 token 既在 `ps` 命令行（全局可见）又在 nginx `access.log` 的 URL query（今日 52 条 / 昨日 585 条）；③ `xiaoyao-backend` 的 `FLASK_SECRET_KEY` 在容器 env 里（docker 组成员可读）；④ `syncserver.env`/`config.json` 里是同步账号明文（权限 600/640 正确）。可读边界：`<SSH用户>` 在 `adm` 组，journal 与 `/var/log/nginx` 都读得到；**`google-cloud-ops-agent` 是 inactive+masked，日志未外传**。
- 可能的原因：lark SDK 与 komari 都把连接 URL 原样 INFO 输出；agent 用命令行传 token 是其默认用法；没有做日志脱敏或 `access_log off`。
- 建议怎么处理：① 视风险接受度决定——真正需要动作的是「别让这些日志离开本机」（当前没外传，且没配任何日志上传）；② 想收口的话，nginx 给 `/api/clients/v2/rpc` 加 `access_log off;`，并对 komari agent token 做一次轮换（**轮换=改配置+重启服务，需授权**）；③ 把「日志含 token」写进交接清单，避免以后有人开了 ops-agent 就把凭据推到云上。

**🟡-4　对外暴露面里有一个「本机无法审计」的部分**
- 发现了什么：`cloudflared` 用的是**远端托管隧道**（`/etc/cloudflared/` 只有 `tunnel-token`，**没有本地 config.yml**，ingress 在 Cloudflare 侧），而连接指引显示设备走 `https://anki.example.com`、还有 `https://anki-status.example.com`。也就是说 8080/8099 通过隧道在公网有门，但**这台机器上没有任何文件能证明现在暴露了哪些子域、有没有 Cloudflare Access 策略**。同时 nginx 那侧 `status.example.com` 是**纯反代、无应用层鉴权/限速**（依赖 komari 自身登录），3 天内已被扫 `/.env`、`/.git`、`/wp-admin` 等 60 次。iptables 只约束 80/443，22 与 GCP agent 的随机端口没有本地入站规则。
- 可能的原因：隧道从「本地 config」迁到了「CF 远端配置」（本机零配置更省事），但没有把结论抄回文档；GCP VPC 防火墙规则同样在云上，VM 内看不见。
- 建议怎么处理：① 去 Cloudflare Zero Trust 控制台核一次 Tunnel → Public hostname 列表 + 是否有 Access 策略，把结果写进交接文档（一次 5 分钟的核对）；② 去 GCP 控制台核 VPC 防火墙是否只放 22（把 80/443 交给 CF）；③ 若想让 SSH 也收敛：优先用 GCP 防火墙按源 IP/tag 限 22（**不建议装 fail2ban**：这台机内存只剩 220MB 可用，多一个常驻进程不划算）。

**🟡-5　最小权限只做到了一半：hermes 没 sudo 但在 docker 组**
- 发现了什么：`sudo -l -U hermes` = **not allowed**（`/etc/sudoers.d/hermes-agent` 现在只剩注释，mtime 09-26 18:39）；但 `docker:x:1001:<SSH用户>,hermes,workbuddy-ai-agent` —— docker 组等价 root。另外 `/etc/sudoers.d/90-codex-temporary`（09-05，`<SSH用户> NOPASSWD: ALL`）还挂着，名字写着 temporary，和 `%google-sudoers NOPASSWD: ALL`（成员 <SSH用户>、workbuddy-ai-agent）重复授权；`<SSH用户>` 还在 `lxd` 组。OS Login 侧目前不是入口（`enable-oslogin` 元数据未设置、`google-oslogin-cache` inactive、`trustedusercakeys none`）。
- 可能的原因：多任 agent 各加自己的授权（codex 临时、hermes-agent、workbuddy-ai-agent、GCP 默认），只加不减；上一轮把 sudo 收了，没意识到组权限是另一条路。
- 建议怎么处理：分两步、每步都要授权并带回归验证——① 低风险：删 `90-codex-temporary`（`sudo -l` 对 <SSH用户> 的能力不变，因为 google-sudoers 那条还在）；② 中风险：把 hermes 移出 docker 组（制卡链路不碰 docker；Wallos/Komari 走 HTTP/MCP，实测 hermes 用 docker 的次数为 0），移出后必须跑一次完整链路回归（飞书发消息→制卡→手机同步→媒体核对两行 0）。③ 顺带把同步副本从 0644 改 640（详见 🟢-5）。

**🟡-6　备份产物在膨胀，且 `pre-*` 手工快照没有保留策略**
- 发现了什么：`anki-sync-*.tar.gz` 从 09-20～09-25 的 132–142MB 跳到 09-26 的 **251.5MB**（媒体从 7260→7627 个文件、286,696,785 字节的对应增长，且 tar 里连 `-wal/-shm` 一起打进去）；`backups/` 还有 **12 份 `pre-*.anki2`（每份 ~60MB）**，命名各异、无清理逻辑；`/var/lib/anki-autocards` 已 3.2GB。近 7 天新建/改写 5.22GB。
- 可能的原因：备份设计只给每日 tar 定了 `KEEP=7`，`pre-*` 是各任 agent 操作前手放的，从来没人负责回收；tar 未排除边车文件。
- 建议怎么处理：`pre-*` 保留最近 3 份 + 有 `README-<字母>.txt` 的版本快照，其余归档或删除；tar 加 `--exclude='*-wal' --exclude='*-shm'`（能压回约 150MB 量级，需实测一次才给准数）；顺带 `docker image prune`（可回收 542MB 镜像 + 137MB 构建缓存，**属删除操作，需授权**）。

**🟡-7　模型只有一个服务商、没有故障转移**
- 发现了什么：`custom_providers` 仅 SiliconFlow 一项，`fallback_model` 整段注释；`terminal.backend=local`，制卡/提醒/cron 全依赖这一个 API。
- 可能的原因：配置期只挑了性价比路线；Hermes 支持 fallback 但没启用。
- 建议怎么处理：如果你能接受「SiliconFlow 挂了当天制卡不可用」，就保持现状，只在 SKILL 里加一句「模型调用失败→飞书回一句而不是静默」；不能接受就在 `fallback_model` 里配第二家（需要第二家的 key，属配置变更+需授权）。

**🟡-8　对话式执行的审批闸是关的（tirith 部分见下方更正）**
- 发现了什么：`approvals.mode: 'off'`（对话式执行不审批）、`updates.pre_update_backup=false`；但 USER.md/MEMORY.md 里写着「写操作要批准」「改前先备份」——这条链全靠模型自觉。`cron_mode`/`unattended_mode` 是 `approve`（无人值守场景要审批）。
- **⚠ 更正**：我上一版写「`tirith` 未安装、机器侧拦截为空」是错的。第三轮实测：`/home/hermes/.hermes/bin/tirith` 是 39MB 的可执行 ELF，`tirith --version` → `0.4.1`；`tools/tirith_security.py` 的默认解析是「先 PATH、再兜底 `$HERMES_HOME/bin/tirith`」，且 `tirith_enabled` 默认 true、`tirith_fail_open` 默认 true → **预执行扫描器存在且按默认配置处于启用路径上**。限制是：14 天日志里 **0 条 tirith 记录**，所以「它是否真的在每次命令执行时被调用、拦过什么」无法从既有日志证实（要证实需主动做一次带副作用的触发测试，本轮没做）。

- 建议怎么处理：优先级排序是「组权限(🟡-5) > approvals.mode」。我的建议是保持 `off`（写了卡随时能撤销，命令执行才是关键面），配合 🟡-5 的收口；`pre_update_backup=true` 值得改（一行配置，成本是 104MB/次磁盘）。另外 tirith 是否在链路上生效，可以用一次「故意给它一条会被标记的命令」的方式验证——那是带副作用的测试，需要你授权。
